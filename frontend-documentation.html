🏗️ Frontend Architecture

Architecture Pattern: Component-Based Architecture with Service Layer
Design Philosophy: Separation of Concerns, Reusability, Type Safety

Architecture Layers

User Interaction ↓ React Components (Pages/Layouts) ↓ React Router (Navigation) ↓ Services Layer (API calls) ↓ Axios Interceptors (Auth tokens) ↓ Backend API ↓ State Management (Zustand stores) ↓ Component Re-render ↓ Socket.io (Real-time updates) ↓ UI Updates

Data Flow

1. User Action → Service Call

User clicks button → Component calls service function → Service makes API request

2. API Response → State Update

API returns data → Service processes response → Zustand store updated → Components re-render

3. Real-time Updates

Socket.io receives event → Notification store updated → Toast notification shown → UI refreshed

🛣️ Routing & Navigation

Route Structure

Public Routes No Auth Required

/login - User login page /register - User registration page

Student Routes Student Role

/student/dashboard - Student dashboard with stats /student/create-outpass - Create new outpass request /student/outpass-history - View all outpasses /student/outpass/:id - View specific outpass details /student/profile - Student profile & settings

Warden Routes Warden Role

/warden/dashboard - Warden dashboard with stats /warden/pending-requests - Pending outpass approvals /warden/all-outpasses - All outpasses in hostel /warden/outpass/:id - View & approve/reject outpass /warden/profile - Warden profile & settings

Security Routes Security Role

/security/dashboard - Security dashboard with stats /security/scan-qr - QR code scanner for check-in/out /security/active-passes - Currently checked-out students /security/history - Check-in/out history /security/profile - Security profile & settings

Route Protection

Protected Routes: All routes except /login and /register require authentication
Role-Based Access: Routes are protected by user role (student, warden, security)
Redirect Logic: Unauthenticated users → /login, Wrong role → /unauthorized

📦 State Management

Zustand Stores

Auth Store (authStore.ts)

Purpose: Manage authentication state

State: - user: User | null - token: string | null - isAuthenticated: boolean Actions: - login(user, token) - logout() - updateUser(user)

Notification Store (notificationStore.ts)

Purpose: Manage notifications

State: - notifications: Notification[] - unreadCount: number Actions: - addNotification(notification) - markAsRead(id) - clearAll()

State Persistence

LocalStorage: Auth token persisted for session management
Session Management: Token validated on app load, auto-logout on expiry

🔧 Services Layer

API Service (api.ts)

Axios Instance Configuration

Base URL: process.env.VITE_API_URL Timeout: 10000ms Request Interceptor: - Attach JWT token to Authorization header - Add Content-Type: application/json Response Interceptor: - Handle 401 (Unauthorized) → Auto logout - Handle 403 (Forbidden) → Redirect to unauthorized - Handle network errors → Show error toast

Auth Service (auth.service.ts)

Authentication Operations

login(email, password) - POST /api/auth/login - Returns: { user, token } register(userData) - POST /api/auth/register - Returns: { user, token } getProfile() - GET /api/auth/profile - Returns: { user } updateProfile(data) - PUT /api/auth/profile - Returns: { user }

Outpass Service (outpass.service.ts)

Outpass CRUD Operations

createOutpass(data) - POST /api/student/outpasses - Returns: { outpass } getMyOutpasses(filters) - GET /api/student/outpasses - Returns: { outpasses, pagination } getOutpassById(id) - GET /api/student/outpass/:id - Returns: { outpass } approveOutpass(id, remarks) - PATCH /api/warden/outpass/:id/approve - Returns: { outpass } rejectOutpass(id, reason) - PATCH /api/warden/outpass/:id/reject - Returns: { outpass } checkOut(outpassId) - POST /api/security/check-out - Returns: { success } checkIn(outpassId) - POST /api/security/check-in - Returns: { success }

Socket Service (socket.service.ts)

Real-time Communication

connect(token) - Establish WebSocket connection - Authenticate with JWT token Events Listened: - 'notification' → New notification received - 'outpass:created' → New outpass created - 'outpass:approved' → Outpass approved - 'outpass:rejected' → Outpass rejected - 'outpass:checked-out' → Student checked out - 'outpass:checked-in' → Student checked in disconnect() - Close WebSocket connection

Notification Service (notification.service.ts)

Notification Operations

getNotifications() - GET /api/notifications - Returns: { notifications } markAsRead(id) - PATCH /api/notifications/:id/read - Returns: { success } deleteNotification(id) - DELETE /api/notifications/:id - Returns: { success }

🔄 User Workflows

1. Student Creates Outpass

1. Student logs in → Redirected to /student/dashboard 2. Clicks "Create Outpass" → Navigate to /student/create-outpass 3. Fills form (reason, dates, destination, etc.) 4. Form validated with Zod schema 5. Submit → outpassService.createOutpass() 6. API call → Backend creates outpass 7. Success toast shown 8. Socket.io emits 'outpass:created' event 9. Warden receives real-time notification 10. Student redirected to /student/outpass-history

2. Warden Approves Outpass

1. Warden receives notification (Socket.io) 2. Clicks notification → Navigate to /warden/pending-requests 3. Views outpass details 4. Clicks "Approve" button 5. Modal opens for remarks 6. Submit → outpassService.approveOutpass() 7. Backend generates QR code 8. Backend sends email with PDF 9. Socket.io emits 'outpass:approved' event 10. Student receives real-time notification 11. Outpass status updated to "Approved"

3. Security Checks Out Student

1. Security officer opens /security/scan-qr 2. Camera activates (html5-qrcode) 3. Student shows QR code 4. QR scanned → Decoded data extracted 5. outpassService.checkOut(outpassId) 6. Backend verifies QR code 7. Backend updates outpass status to "Checked Out" 8. Socket.io emits 'outpass:checked-out' event 9. Student receives notification 10. Success toast shown to security officer
