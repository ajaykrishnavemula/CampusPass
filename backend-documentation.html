🏗️ System Architecture

Architecture Pattern: Layered Architecture (MVC + Services)
Design Philosophy: Separation of Concerns, Single Responsibility Principle

Architecture Layers

1. Entry Point (index.ts)

Server initialization, plugin registration, database connection

2. Routes Layer

HTTP endpoint definitions, route grouping, middleware attachment

3. Middleware Layer

Authentication, validation, error handling, request preprocessing

4. Controllers Layer

Request handling, response formatting, business logic orchestration

5. Services Layer

Business logic, external service integration, complex operations

6. Models Layer

Data schemas, database operations, data validation

7. Database (MongoDB)

Data persistence, queries, transactions

Component Interaction

Client Request ↓ Fastify Server (index.ts) ↓ CORS & Security Middleware (helmet, cors) ↓ Rate Limiting (100 req/15min) ↓ Routes (auth, outpass, notification) ↓ Authentication Middleware (JWT verification) ↓ Validation Middleware (Zod schemas) ↓ Controllers (business logic orchestration) ↓ Services (AuthService, OutpassService, etc.) ↓ Models (User, Outpass, Notification) ↓ MongoDB Database ↓ Response back through layers ↓ Socket.io (real-time notifications) ↓ Client receives response + live updates

🔄 Application Logic Flow

1. Server Startup Flow

Step 1: Load Environment Variables

dotenv loads .env file → Configuration available

Step 2: Create Fastify Instance

Initialize with logger, trust proxy settings

Step 3: Register Security Plugins

CORS → Helmet → JWT → Rate Limiting

Step 4: Connect to MongoDB

Mongoose connects to database, handles connection events

Step 5: Initialize Services

Email Service (SMTP) → Socket.io → Other services

Step 6: Register Routes

/api/auth → /api/outpasses → /api/notifications

Step 7: Set Error Handlers

Global error handler → 404 handler

Step 8: Start Server

Listen on PORT (default: 3000) → Server ready! 🚀

2. Authentication Flow (Login)

1. Client sends POST /api/auth/login Body: { email, password } 2. Request hits auth.routes.ts → Routes to auth.controller.ts → login() 3. Controller validates input → Checks if user exists in database 4. AuthService.comparePassword() → bcrypt compares hashed password 5. If valid: → Generate JWT token (expires in 7 days) → Return user data + token 6. Client stores token → Includes in Authorization header for future requests 7. Protected routes verify token via auth.middleware.ts → Decodes JWT → Attaches user to request object

3. Outpass Creation Flow (Student)

Step 1: Student Creates Outpass

POST /api/outpasses with details (destination, dates, purpose)

Step 2: Validation

Middleware validates request body using Zod schema

Step 3: Controller Processing

student.controller.ts → createOutpass()

Step 4: Service Layer

OutpassService creates outpass with status: PENDING

Step 5: Generate QR Code

QRService generates unique QR code for outpass

Step 6: Save to Database

Outpass model saves to MongoDB

Step 7: Create Notification

NotificationService notifies warden of new request

Step 8: Real-time Update

SocketService emits 'outpass:created' event to warden

Step 9: Email Notification

EmailService sends email to warden (if configured)

4. Outpass Approval Flow (Warden)

1. Warden receives notification (Socket.io + Email) 2. Warden views pending outpasses GET /api/outpasses/pending 3. Warden approves outpass POST /api/outpasses/:id/approve Body: { remarks: "Approved for valid reason" } 4. warden.controller.ts → approveOutpass() 5. OutpassService updates: • status: PENDING → APPROVED • approvedAt: current timestamp • warden: warden's user ID • wardenRemarks: approval message 6. Generate PDF with QR code PDFService creates printable outpass document 7. Create notifications: • Student: "Your outpass has been approved" • Security: "New approved outpass available" 8. Real-time updates: • Socket.io emits 'outpass:approved' to student • Socket.io emits to security personnel 9. Email notifications: • Student receives approval email with PDF attachment • Security receives notification 10. Student can now download PDF and show at gate

5. Check-Out Flow (Security)

Step 1: Student Arrives at Gate

Shows QR code (from PDF or mobile app)

Step 2: Security Scans QR

POST /api/outpasses/verify-qr with QR data

Step 3: QR Verification

QRService validates QR code authenticity

Step 4: Outpass Validation

Check: status=APPROVED, dates valid, not expired

Step 5: Check-Out

POST /api/outpasses/:id/checkout

Step 6: Update Status

status: APPROVED → CHECKED_OUT, checkOutTime: now

Step 7: Notifications

Student, Warden receive check-out notification

Step 8: Real-time Update

Socket.io broadcasts 'outpass:checked_out' event

6. Real-time Notification Flow

Socket.io Event Flow: 1. Client connects to WebSocket ws://localhost:3000 2. Server authenticates connection Verifies JWT token from handshake 3. User joins role-specific rooms: • Students: room "student-{userId}" • Wardens: room "warden-{hostel}" • Security: room "security" 4. When event occurs (e.g., outpass approved): a) Service layer triggers event SocketService.emitOutpassApproved(outpass) b) Socket.io emits to specific rooms: io.to(`student-${studentId}`).emit('outpass:approved', data) io.to(`security`).emit('outpass:approved', data) c) Connected clients receive event instantly Client updates UI in real-time 5. Notification also saved to database For users who are offline 6. When user comes online: Fetches unread notifications GET /api/notifications?unread=true

📊 Data Models

User Model

interface IUser { // Basic Info email: string; // Unique email password: string; // Hashed with bcrypt name: string; // Full name role: UserRole; // 0=Student, 1=Admin, 2=Warden, 3=Security phone?: string; // Contact number // Student-specific hostel?: string; // Hostel name roomNumber?: string; // Room number department?: string; // Academic department year?: number; // Academic year rollNumber?: string; // Student ID gender?: string; // Gender remarkScore?: number; // Behavior score inCampus?: boolean; // Currently in campus // Status isActive: boolean; // Account active/inactive photoUrl?: string; // Profile picture // Timestamps createdAt: Date; updatedAt: Date; } Roles: • STUDENT (0): Create outpasses, view own history • ADMIN (1): Full system access • WARDEN (2): Approve/reject outpasses for their hostel • SECURITY (3): Check-in/out students, verify QR codes

Outpass Model

interface IOutpass { // References student: ObjectId; // Reference to User warden?: ObjectId; // Approving warden checkOutBy?: ObjectId; // Security who checked out checkInBy?: ObjectId; // Security who checked in // Outpass Details outpassNumber: string; // Unique identifier (auto-generated) type: OutpassType; // local, home, emergency, medical, other purpose: string; // Reason for outpass destination: string; // Where student is going // Dates fromDate: Date; // Start date/time toDate: Date; // Expected return date/time // Status & Approval status: OutpassStatus; // pending, approved, rejected, etc. wardenRemarks?: string; // Warden's comments approvedAt?: Date; // Approval timestamp rejectedAt?: Date; // Rejection timestamp rejectionReason?: string; // Why rejected // Check-in/out checkOutTime?: Date; // When student left checkInTime?: Date; // When student returned // Security qrCode?: string; // QR code data isOverdue: boolean; // Past return date // Timestamps createdAt: Date; updatedAt: Date; } Status Flow: PENDING → APPROVED → CHECKED_OUT → CHECKED_IN ↓ REJECTED ↓ CANCELLED (by student) ↓ OVERDUE (past return date)

Notification Model

interface INotification { user: ObjectId; // Recipient user title: string; // Notification title message: string; // Notification content type: string; // outpass, system, alert relatedOutpass?: ObjectId; // Link to outpass if relevant isRead: boolean; // Read status createdAt: Date; updatedAt: Date; } Notification Types: • outpass_created: New outpass request • outpass_approved: Outpass approved • outpass_rejected: Outpass rejected • outpass_checked_out: Student checked out • outpass_checked_in: Student checked in • outpass_overdue: Outpass overdue • system_alert: System-wide announcement

🔌 Real-time Communication (Socket.io)

Why Socket.io? Enables instant, bidirectional communication between server and clients. Perfect for real-time notifications, live updates, and collaborative features.

Connection Flow

1. Client Initiates Connection

Frontend connects to ws://localhost:3000 with JWT token

2. Server Authentication

Middleware verifies JWT token from handshake auth

3. User Identification

Extract user ID and role from decoded token

4. Room Assignment

Join role-specific rooms based on user type

5. Connection Established

Client ready to receive real-time events

Room Structure

Room Hierarchy: 1. User-specific rooms: • student-{userId} → Individual student • warden-{userId} → Individual warden • security-{userId} → Individual security 2. Role-based rooms: • students → All students • wardens → All wardens • security → All security personnel • admins → All administrators 3. Hostel-based rooms: • hostel-{hostelName} → All users in a hostel • warden-hostel-{name} → Warden's hostel 4. Global room: • all-users → System-wide broadcasts

✨ Best Practices & Patterns

1. Error Handling

// Centralized Error Handler (error.middleware.ts) export const errorHandler = ( error: Error, request: FastifyRequest, reply: FastifyReply ) => { // Log error logger.error({ error: error.message, stack: error.stack, path: request.url, method: request.method }); // Determine status code const statusCode = error.statusCode || 500; // Send response reply.code(statusCode).send({ success: false, error: error.message, ...(process.env.NODE_ENV === 'development' && { stack: error.stack }) }); }; // Usage in Controllers try { const result = await service.doSomething(); return reply.send({ success: true, data: result }); } catch (error) { throw new Error('Operation failed: ' + error.message); }

2. Input Validation

// Using Zod for Schema Validation import { z } from 'zod'; const createOutpassSchema = z.object({ type: z.enum(['local', 'home', 'emergency', 'medical', 'other']), purpose: z.string().min(10).max(500), destination: z.string().min(3).max(200), fromDate: z.string().datetime(), toDate: z.string().datetime() }).refine( (data) => new Date(data.toDate) > new Date(data.fromDate), { message: 'Return date must be after departure date' } ); // Validation Middleware export const validateRequest = (schema: z.ZodSchema) => { return async (request: FastifyRequest, reply: FastifyReply) => { try { schema.parse(request.body); } catch (error) { return reply.code(400).send({ success: false, error: 'Validation failed', details: error.errors }); } }; };

3. Authentication Middleware

// JWT Verification export const authenticate = async ( request: FastifyRequest, reply: FastifyReply ) => { try { // Extract token const token = request.headers.authorization?.replace('Bearer ', ''); if (!token) { return reply.code(401).send({ success: false, error: 'No token provided' }); } // Verify token const decoded = await request.server.jwt.verify(token); // Attach user to request request.user = decoded; } catch (error) { return reply.code(401).send({ success: false, error: 'Invalid or expired token' }); } }; // Role-based Authorization export const authorize = (...roles: UserRole[]) => { return async (request: FastifyRequest, reply: FastifyReply) => { if (!roles.includes(request.user.role)) { return reply.code(403).send({ success: false, error: 'Insufficient permissions' }); } }; };

4. Database Queries

🔧 Troubleshooting Guide

Common Issues

Issue: MongoDB Connection Failed

Error: MongooseServerSelectionError: connect ECONNREFUSED

Solutions:

  • Check if MongoDB is running: mongod --version
  • Verify MONGODB_URI in .env file
  • Check network connectivity
  • Ensure MongoDB port (27017) is not blocked

Issue: JWT Token Invalid

Error: JsonWebTokenError: invalid signature

Solutions:

  • Ensure JWT_SECRET matches between frontend and backend
  • Check token expiration (JWT_EXPIRES_IN)
  • Verify token format: "Bearer {token}"
  • Clear browser localStorage and re-login

Issue: CORS Error

Error: Access-Control-Allow-Origin header missing

Solutions:

  • Set FRONTEND_URL in .env to match frontend origin
  • Enable credentials: true in CORS config
  • Check if frontend is running on correct port
  • Verify CORS middleware is registered before routes

Issue: Socket.io Not Connecting

Error: WebSocket connection failed

Solutions:

  • Check if server is running on correct port
  • Verify JWT token is included in handshake
  • Check firewall/proxy settings
  • Enable transports: ['websocket', 'polling']

Issue: Email Not Sending

Error: SMTP connection failed

Solutions:

  • Verify SMTP credentials in .env
  • Enable "Less secure app access" for Gmail
  • Use App Password instead of regular password
  • Check SMTP_PORT (587 for TLS, 465 for SSL)
